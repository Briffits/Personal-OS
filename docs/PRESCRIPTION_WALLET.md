# Prescription Wallet domain and migration

`app/src/prescriptions/prescription.ts` defines metadata, stable record IDs, opaque document/candidate IDs, real calendar-date validation and derived expiry. `prescriptionService.ts` orchestrates a collection through injected storage and document capabilities. It has no Medication imports, medication persistence, native paths, network access or new dependencies. Medication IDs are relationships only; the wallet does not validate their existence or own their records.

`addPrescription(metadata)` creates an independent record without replacing another. `replaceDocument(recordId)` asks for confirmation and retains the record ID and metadata. `deletePrescription(recordId)` asks for confirmation before removing the record. `viewPrescription(recordId)` resolves its current document ID on each invocation. Unknown records fail before document operations. Expired records remain available. There is no inactive state, automatic deletion or medical interpretation.

The service returns saved versus cleanup-pending outcomes after durable import, and preserves that outcome if candidate release fails. Explicit release and cleanup retries are available. Read, confirmation and viewer errors propagate; selection, confirmation and import commit failures are represented in import results. Mutations are blocked while durable cleanup is pending; retained documents can still be viewed. One service instance per store serialises in-process operations; adapters must additionally enforce durable transaction integrity.

## Native migration still required

`updatePrescription(recordId, metadata)` validates a complete replacement metadata value using the existing validator, resolves the retained record and calls atomic `updateMetadata(expectedRecord, metadata)`. It returns the updated record and propagates validation, unknown-ID, pending-cleanup and transaction errors. Both record and document IDs remain unchanged; omitted optional dates are removed. It never selects, opens, replaces or releases documents/candidates, requests confirmation or runs cleanup.

The durable metadata transaction must reject pending cleanup and compare every field of the complete expected existing record (including both IDs, kind, medication links and optional dates) by value inside the transaction. Unknown or stale records fail without mutation. A concurrent metadata edit, document replacement, deletion or newly pending cleanup must not be overwritten. The service's in-process lock alone cannot provide this guarantee.

The `PrescriptionWalletNativeModule` TypeScript interface describes the intended boundary. It is not connected to `NativeModules`. The existing `NativePrescriptionDocuments`, `currentPrescriptionService.ts` and `PrescriptionWalletScreen` remain the tested legacy single-current-document path. The screen still places prescription actions alongside stock controls; this is transitional UI, not the new domain model.

The Swift migration must:

1. Replace the single `current` pointer with protected, backup-excluded collection metadata containing stable record IDs, opaque document IDs and validated metadata, plus a durable cleanup journal. Validate responses at the TypeScript adapter boundary and return only public fields.
2. Implement atomic `create(candidate, metadata)`, `replace(candidate, expectedRecord)`, `updateMetadata(expectedRecord, metadata)` and `remove(expectedRecord)`. Allocate fresh record IDs only for creation. Replacement allocates a fresh document ID and changes no other record fields. Metadata updates preserve both IDs and change only validated metadata, without touching documents, candidates or cleanup. Compare the complete expected record within the native transaction so stale snapshots cannot overwrite newer state. Reject mutations while cleanup is pending.
3. Commit the collection change and cleanup journal together. Failed commits preserve existing records and remove partial imported copies. Recover interrupted commits and remove orphan copies without deleting any retained or journalled document. Deletion must support an empty collection with pending cleanup.
4. Make cleanup idempotent and retryable, removing only journalled documents unreferenced by any retained record. Preserve remaining journal entries on failure. Candidate release must never delete an original source or committed document; recover orphan candidates after interruption.
5. Retain complete file protection and backup exclusion for every candidate, document, directory, metadata file and journal. Keep native errors sanitised. Open only currently referenced document IDs; reject superseded/deleted IDs even when their files await cleanup. Never return filesystem paths.
6. Migrate existing documents without losing them. Legacy records lack a required expiry date: obtain explicit user-supplied metadata rather than guessing dates, kinds or medication links. Keep the legacy document protected and accessible until migration is durably complete.
7. Migrate the screen to a prescription collection with metadata entry and independent metadata editing, per-record viewing/replacement/deletion and confirmation for replacement/deletion. Separate Medication stock controls from wallet presentation. Do not connect the collection service to the legacy `commit(candidate)` operation, which would silently replace unrelated records.

TypeScript unit tests exercise domain workflows with an injected test store. They do not prove Swift crash recovery, on-device file protection, backup exclusion, Files permissions, Quick Look or Face ID. These require native integration and device testing during migration. Existing stock, native boundary and legacy workflow tests remain applicable and are retained.
